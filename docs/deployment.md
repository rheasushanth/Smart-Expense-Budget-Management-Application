# Deployment

**Project:** Smart Expense & Budget Management Application
**Group:** G-15
**Platform:** Render
**Issue:** #70

The environment is defined by [`render.yaml`](../render.yaml) at the repository root,
so it can be recreated from the repository rather than reconstructed from a dashboard.
This page is the procedure TC-POL-01 (NFR-007) reviews.

## What is defined

| Component | Detail |
| --- | --- |
| Web service | `smart-expense`, Python runtime, free plan, Singapore region |
| Database | `smart-expense-db`, PostgreSQL, free plan |
| Root directory | `G15/04_IMPLEMENTATION_TESTING/source-code` |
| Build | `pip install -r requirements.txt && ./build.sh` — installs, collects static files, migrates |
| Start | `gunicorn config.wsgi:application` |
| Health check | `/healthz/` — Render restarts the service if this stops returning 200 |

## Environment variables

| Variable | Source |
| --- | --- |
| `DJANGO_SECRET_KEY` | Generated by Render, held in the service, never in the repository |
| `DJANGO_DEBUG` | `False`, stated explicitly as well as being the default since #61 |
| `DJANGO_ALLOWED_HOSTS` | Resolved from the service, but to its **internal** hostname (`smart-expense-pz56`), not the public one. `settings.py` appends `RENDER_EXTERNAL_HOSTNAME`, which Render publishes to the running container, for the name requests actually arrive on |
| `DATABASE_URL` | Resolved from the database service |

## Creating it

1. Render dashboard → **New** → **Blueprint**, pointed at this repository.
2. Confirm the two services it proposes, and apply.
3. Wait for the first build; check `/healthz/` returns `{"status": "ok", "database": "ok"}`.

Migrations run on every deploy through `build.sh`, so no manual migration step is needed.

## Seeding the load-test dataset

TC-PERF-01 needs 10 000 transactions in the deployed database. From the Render shell:

```bash
python manage.py seed_perf_data --password '<choose one>'
```

The password is supplied on the command line and never stored in the repository. See [`performance/README.md`](../G15/04_IMPLEMENTATION_TESTING/source-code/performance/README.md) for the full TC-PERF-01 procedure.

## Known constraints of the free plan

These affect how the non-functional cases must be run, and are recorded here rather than discovered during testing.

**The web service sleeps after 15 minutes of inactivity**, and a cold start takes roughly 50 seconds. Two consequences:

- **TC-PERF-01** must be run against a warmed service. Issue a request and let it respond before starting Locust, or the first measurements record the cold start rather than the application.
- **TC-AVAIL-01** polls every 5 minutes, which is inside the 15-minute idle window, so the polling itself keeps the service awake once started. The first poll after a quiet period may still record a slow response.

**The free PostgreSQL instance expires 30 days after creation.** TC-AVAIL-01 needs 7 days of polling, so this is not a constraint for the current test window, but the expiry date should be noted against the final report.

### Public deployment access — D-08

The Render deployment is publicly accessible, and registration is open. The deployment has not been restricted because evaluators need to be able to open the URL directly.

The URL is unlisted, which limits discovery, but this does not prevent anyone with the URL from accessing the application or registering. It must not be treated as access control.

This access arrangement is documented under **D-08 in `G15/DEVIATIONS.md`**. Confirmation from the project guide is pending on whether public access is acceptable for the project.

Until the guide confirms acceptance, TC-POL-01 item 4 remains unmet and TC-POL-01 remains **Partial**. If the guide approves the public-access arrangement, item 4 may be marked Pass and D-08 closed.
